市面上已经有很多 Agent Skill 管理工具了，我还是想自己写。

我想要的是一个非侵入式，纯管理的 App。也就是在现有文件系统上覆盖一层薄薄的软件，它只需要反映 Agent Skill 的存在情况，让我可以查看 Skill 的内容，并做适当的管理就行（比如将某个技能软链接给一个 Coding Agent）。这个需求看起来很简单，但苦痛之路开始了，我一直在遭遇 bug。

最初的设计是，不用任何数据库，甚至连 SQLite 这样轻量级的数据库也不用。只用一个 cache 文件存放扫描到的 Agent Skill 结果。然后你就会开始想念数据库的好了。数据库至少能提供事务、Schema 和并发控制，替你挡住一些愚蠢操作。当你将数据库换成一个裸文件，很多麻烦就暴露出来了。如果你的写入不规范、不原子，缓存文件就会被错误地更新，缓存状态就会变脏，前端操作就会卡住、报错。然后就是不停地 fix bugs，直到把问题都解决。

当我们终于解决缓存文件的问题，下一个麻烦又来了。为了让文件系统的变化在 App 中实时反馈，比如往 ~/.claude/skills 里手动添加一个新 skill 时，App 上同步显示这个技能卡片。我给 App 加了文件监控（rust notify crate），这又引入了新的问题。因为 App 的状态变成实时更新，这对状态对齐的要求更高了。现在我们有四层状态：文件系统、内存、cache 文件、App 前端。任何一层出现不一致，哪怕是更新得慢一点，就会导致 bug。这种程度的问题，如果是只有小学二年级 rust 水平的我，肯定是解决不了的，还好有 codex，让它帮我写了手动管理内存的代码，终于勉强对齐了四层状态。

我感觉我对 bug 太过敏感了，几乎每天都能发现新 bug。楼主又不是闲狗，楼主要上班。每天在上班时间使用它发现有 bug 的时候，都感觉有蚂蚁在身上爬，恨不得马上回家修复 bug，发布新版本。有些 bug 是因为 ai 蠢，有些是因为上下文管理不好。当然也有一些是楼主跟不理解代码细节的啥比老板一样，做了一些错误的架构设计，导致 App 变成了 bug 生产机，这时候就要上回退 commit、重构小连招。

我真没想到在 vibe coding 极度发达的今天，写一个没有 bug 的 App 这么难。也许我的出发点就错了，在这个软件极易获得的时代，大多数 App 就是一种快消品，让一个软件达到 70 分就够了，追求 99 分是一种固执。
